# ADR 012 — OpenTofu owns the identity/secret bootstrap handshake (L3)

## Status
Accepted

## Context

[ADR 003](./003-opentofu-vs-terraform-vs-pulumi) chose OpenTofu for the IaC layer with an explicit intent: OpenTofu's footprint inside Atlas should be tiny — just enough to install Argo CD and let it take over. [ADR 004](./004-argocd-vs-flux) reinforced this: Argo CD's app-of-apps owns every workload; OpenTofu does not.

When sequencing the actual installation, an unavoidable handshake step emerged between two of the platform's services:

1. Authentik ([ADR 008](./008-authentik-oidc)) is the OIDC IdP for every other public service.
2. Infisical ([ADR 009](./009-infisical-secrets)) is the secret store that ESO syncs into Kubernetes.
3. Every identity-aware service (Harbor, Grafana, Argo CD, Infisical's own web UI, Traefik dashboard) needs an `OIDC_CLIENT_SECRET` that is *generated by Authentik* and *stored in Infisical*.
4. This handshake must happen *after* Authentik and Infisical are running, but *before* Argo CD can deploy the identity-aware workloads.

It is the only stateful coupling in the otherwise pure-GitOps flow. Two options exist:

1. **Expand OpenTofu's scope.** A second `tofu apply` runs after Argo CD has brought Authentik and Infisical up, using the `goauthentik/authentik` and `infisical/infisical` providers to declaratively create OIDC applications and store their resulting secrets in Infisical. Walks back the minimalism of ADR 003/004.
2. **A bootstrap Job inside the cluster.** A Kubernetes `Job` (delivered via Argo CD with a sync wave that puts it after Authentik/Infisical and before the identity-aware apps) runs an imperative script that hits both APIs. Keeps OpenTofu tiny, but moves orchestration into a custom container.

## Decision

**Expand OpenTofu's scope** to own the L3 handshake. A second `tofu apply -target=module.l3` step is part of the documented bootstrap procedure ([Getting Started → L3](../getting-started#l3-the-identity-secret-handshake-detailed)). The Authentik and Infisical Terraform providers are added to the IaC repository.

## Consequences

### Positive
- **Declarative.** Every OIDC application is a tracked resource with diffable state. Renaming a redirect URI is a normal IaC change, not a script edit.
- **Idempotent.** Re-running `tofu apply` reconciles drift — if someone rotates a client secret in the Authentik UI, the next apply re-syncs it into Infisical.
- **No custom container to maintain.** The alternative — a Bash or Python `Job` — would be a small, brittle, hand-maintained piece of imperative code with its own image to build and patch.
- **The same trust boundary as the rest of OpenTofu.** The L3 apply runs from the operator's laptop using API tokens already sourced from the password manager. No cluster-internal service account needs API-creating power on Authentik or Infisical.
- **One place to grep for "what OIDC clients exist".** `atlas-iac/modules/l3/` is canonical; the GitOps repo only consumes the resulting secrets via `ExternalSecret`s.

### Negative
- **OpenTofu is no longer "install Argo CD only".** ADR 003 and ADR 004 stated minimalism as a virtue; this ADR softens that line. The reality is that L3 is a true platform-bootstrap concern, not a workload concern — so the line moved, it didn't disappear.
- **Two `tofu apply` runs are required during bootstrap.** The procedure splits into L1 and L3 with an Argo-CD-driven L2 in between. This is documented but it is a real cognitive cost.
- **State surface grows.** OpenTofu state now contains identifiers for every Authentik OIDC application and every Infisical secret it manages. Losing the state requires `tofu import` cycles to recover, not just a re-run.
- **Two new providers to track.** `goauthentik/authentik` and `infisical/infisical` move on their own release cadences; provider major versions may break.

### Trade-off accepted
The IaC layer becomes ~30 lines bigger and gains a second `apply` step, in exchange for keeping the bootstrap handshake fully declarative, observable, and outside the cluster. Operating a custom bootstrap `Job` for the same purpose would cost more over time than the extra OpenTofu module.

### Why not a bootstrap Job
A bootstrap Job inside the cluster keeps OpenTofu pure, but the resulting imperative script has to handle: idempotency on retry, partial failures (an OIDC app created but its secret not yet pushed to Infisical), drift detection, and an image-pull dependency (the Job's container has to come from somewhere — likely a public registry, since Harbor doesn't exist yet at this stage). All of those are problems Terraform/OpenTofu already solve generically. Reinventing them for one handshake is not worth the marginal purity of "OpenTofu installs only Argo CD".
